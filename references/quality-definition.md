# 知识库质量与验收

本页用于制定与当前任务相称的质量要求，不是每次查询、文档修改或内容更新都必须执行的检查套件。

## 先定义范围

从用户任务确定来源范围、版本、语言、权威顺序和需要支持的问题。输入已明确时不重复询问。不把生成索引、日志、模型文件或旧构建产物当作知识来源。

可复用知识库应保留原始或清理后的来源、来源标识与链接、可读正文及重建所需配置。不要让 Qdrant、FTS 或缓存成为唯一数据源。

## 内容判断

检查与任务有关的代表性材料：

- 来源可追溯，版本和适用范围明确；
- 转换没有丢失重要标题、代码、表格或解释；
- chunk 能提供足够上下文，原始标识符与解释没有被不合理分离；
- fetch 原文能支撑用户需要的答案；
- 媒体保留或压缩以证据可读性为依据，不统一强制转 JPEG、去透明度或删除特定文件名。

来源准备确实改变了语义或可追溯性时，简要说明过滤和转换规则；无需把已有日志、CLI state 和对话记录复制成多份账本。

## 按变更选择检查

下面是用途说明，按用户要求、既有验收约定及实际变更选择，不默认全部运行，也不自动新增测试或门禁。

| 检查 | 直接覆盖的范围 |
|---|---|
| `validate` | manifest、目录与知识库结构 |
| `content lint` | Markdown mirror 的链接、图片等问题 |
| `index verify` / `validate-index` | 派生索引与当前运行时契约的兼容性 |
| 实际 `search` 后 `fetch` | 本次问题的检索与证据获取路径 |
| `smoke-test` / `eval run` | 已有或获授权创建的检索用例 |
| `eval coverage` / `eval compare` | 已标注用例的覆盖、与指定基线的比较 |
| `package verify` | 指定目录或归档的 package 检查；不证明其中没有所有敏感内容 |

Pipeline 执行它自身记录的步骤和检查；先用 `pipeline plan` 查看，完成后读已有 run record，不再机械重复同一套检查。

## 需要检索评测时

优先复用已有 suite。用户要求创建评测时，选取能代表目标工作流的精确标识符、概念、流程或边界问题，不规定固定数量。`mode`、语言、过滤和 rerank 设置应与真实用法一致。

用 `expected_chunk_id` 或 `expected_chunk_ids` 标注已知相关切片；`topic`、`language` 和 `source_id` 可用于覆盖统计。没有相关切片标注的用例不能用于 Recall@K 或 MRR 的结论。

`expected_no_evidence: true` 只断言没有检索结果，不证明模型会拒答，也不判断非空候选能否支撑答案。重要结论仍需核对 fetch 原文。只在接受当前检索行为后更新 baseline，不能为了消除回归而覆盖它。

## 结果与交接

检查结果和退出码的解释见 [command-reference.md](command-reference.md)。说明实际覆盖范围：查询成功不等于整库校验通过，编译或 package 检查不等于检索质量通过。

交接保留定位入口、更新方式、实际验证结果与未完成限制即可。库只支持 keyword 时不要称为 Hybrid-ready；未运行的质量评测不要称为通过。仅在任务需要发布切换或回滚时采用 staging/alias，不要求每个本地库都配置它。
